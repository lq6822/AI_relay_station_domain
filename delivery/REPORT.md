# AI 中转站域名情报生产汇报

**交付日期：2026 年 9 月 20 日。** 本次以公开材料识别向用户提供第三方模型代理、聚合或转发服务的域名，完成 53 个初始候选及 2 个关联候选的分析，共 55 个完整主机名、54 个注册域。标签描述公开业务类型，不表示恶意、违法或获得上游授权。情报、原始分析和复核依据均随本报告提供。

## 一、判定标准：先明确服务类型，再判断证据是否充分

确认一个域名，需要同时回答三个问题：经营者是否区别于所接入模型的原厂；是否向用户提供模型接入服务；是否有明确的多厂商接入、代理或转发说明。判断对象是完整主机名，例如文档站和它介绍的 API 站需要分别判断。

| 标签 | 本次采用的标准 |
| --- | --- |
| 确认 | 三项条件都有当前、主体明确的证据，且没有影响结论的未解决问题。 |
| 疑似 | 有具体中转线索，但条件缺失、来源过旧或仍有业务疑点。 |
| 排除 | 当前材料明确说明是文档、客户端、导航等非目标用途。 |
| 证据不足 | 已开展调查，仍缺少足够方向依据；不能把访问失败直接判为排除。 |

原厂模型服务、开源网关软件、客户端和目录网站可能同时出现模型名称、API Key 或兼容接口。这些词语只能帮助发现候选，不能单独证明站点经营中转服务。公开服务说明可以支持业务类型判断，但本次未付费调用目标站接口，也未验证后台实际转发链路。

`confidence` 表示**所选标签的证据支持程度**，采用 0.55、0.75、0.90 三档，分别对应暂定、有限支持和充分支持。它不是目标概率，也没有经过统计校准。`last_verified` 取支撑当前结论的材料采集时间；重新分析或导出不会自动刷新旧证据。

明确这些边界后，数据整理的重点就从关键词命中转为保存可定位的事实和来源。

## 二、数据、技术方法与 AI 使用

### 2.1 数据从哪里来

初始候选包含 [mn-api 公开目录](https://github.com/mn-api/awesome-ai-proxy)中的 31 个域名、[howardpen9 公开目录](https://github.com/howardpen9/awesome-ai-api-proxy)中去重后选取的 15 个域名，以及 7 个公开服务或边界对照站点。目录用于发现线索，不把目录的收录、价格或维护者判断直接当成当前经营事实。随后访问候选网站，并选取能解释业务类型的短原文。

最终材料来自 59 次独立来源采集，整理为 104 条域名材料：97 条取得可用片段，7 条保留访问或采集失败。一个来源可支持多个域名，因此材料条数不等于网页数。采集发生于交付日北京时间 17:26—17:56；机器记录保留带时区的时间。HTTP 状态、最终地址及成功读取正文的摘要值保存在 [collection.json](collection.json)。

采集脚本顺序发起公开 GET，请求之间间隔 2 秒，设置 20 秒请求超时和 2 MB 正文限制，不执行网页脚本、不登录。遇到证书错误、代理错误、HTTP 错误或正文超限时如实记录，不将其解释成目标网站必然失效。JavaScript 页面只取得静态文本，这也是本次覆盖的明确限制。

### 2.2 一条域名如何形成结论

处理顺序为：**发现线索 → 采集并摘录 → 规范化域名、归属材料 → AI 提取事实 → 校验引用 → 规则判定 → 必要复核 → 导出**。

线索记录发现出处，材料记录原文、访问时间、来源类型和主体关联。跨站材料需要能定位目标完整主机名；重定向后的业务说明不能无条件归给原主机。目录转述标为二手来源，时效未明确的收录标为未知。摘录脚本检查原文和链接是否确实出现在采集记录中。

模型输出事实、引用、疑点及关联链接；最终标签和分数由 `assessment.py` 统一计算。程序检查材料编号、逐字引用、实际链接和主体归属，保留冲突，不以重复出现的次数抵消反证。每完成一个域名就保存批次；中断后从已保存进度继续。没有材料、调用失败或输出不合格属于未完成分析，不伪装成“证据不足”。

### 2.3 AI 参与方式及验证结果

运行时使用 `deepseek-flash`，通过 DeepSeek 的 Chat Completions 接口分析本地材料。地址、模型、Key 和调用限额统一放在 `config/ai.json`。Key 用于向配置的 AI 接口认证，不随材料发送给候选网站，也不进入批次与情报文件。

Agent 只有读取本域材料和提取其中链接两个只读工具。结束前必须读取全部材料及链接；每域最多 5 次请求，格式或引用错误只允许一次修正。网页中的指令按材料内容处理，不能增加工具权限。

AI 编程工具参与代码整理、采集摘录核对和结果复核。本次有 40 条复核记录，实际复核者均明确标为 **Codex AI**，没有独立人工标注集。复核既处理模型提出的疑点，也能主动降低未被模型标记的错误判断。例如软件文档中的“添加上游服务商”被误读成网站经营事实后，依据文档用途修订了结论；出现页面副本标记的站点也从确认降为疑似。

56 项离线测试通过，覆盖引用、四标签、复核、断点继续、扩展和导出等分支。真实首轮有 5 个分析未完成；单独重跑完成 4 个，剩余 1 个在统一元描述特殊空格、重新采集后完成。失败记录保留，未覆盖历史。最终 55 条记录通过结构检查，104 条材料的摘录均核对到本地实际采集记录；用于重跑的输入也已验证，无格式、归属或缺材料问题。

所列交付批次中，成功完成的 55 次分析共记录 177 次模型请求、485,926 个输入 token 和 63,372 个输出 token。该统计不含失败调用和前期小样本验证，不能作为账号总消费。引用检查能够发现伪造原文，不能自动证明语义解释正确；高影响判断、主体不清、冲突及模型误读仍需要人工复核。本次不报告准确率或召回率。

上述处理产生的最终分布为：确认 **15**、疑似 **35**、排除 **4**、证据不足 **1**。较多疑似保留了调查边界，具体判断通过下面的案例说明。

## 三、典型案例与关联扩展

### 3.1 OpenRouter：服务入口和统一调用文档相互对应

`openrouter.ai` 判为**确认，0.90**。[首页](https://openrouter.ai/)提供 API Key 入口和供应商故障切换说明；[调用文档](https://openrouter.ai/docs/quickstart)说明通过统一 API 使用多种模型，并给出该主机下的请求端点。品牌与外部模型提供方可区分，用户接入和上游路由也有直接说明，三项条件能够对应到当前材料。该结论确认公开业务类型，未验证实际路由质量或供应商授权。

### 3.2 AIHubMix：多厂商接入与本域端点形成证据链

`aihubmix.com` 判为**确认，0.90**。[首页](https://aihubmix.com/)说明通过统一端点接入 ChatGPT、Claude、Gemini、DeepSeek 等模型，提供 Key 获取入口，并出现本域的 `/v1/chat/completions` 地址。这里的依据包含服务形态和接入入口，超出了单纯罗列模型名称；因此能够支持第三方身份、用户接入和聚合关系。

### 3.3 从确认种子发现新主机，再独立判断

本次对 13 个确认种子的已采集链接进行一轮整理，新增 2 个候选，均来自 [UIUIAPI 首页](https://uiuiapi.com/)明确列出的控制台和备用入口。

| 新候选 | 关联依据 | 独立调查结果 |
| --- | --- | --- |
| `api.uiuihao.com` | 种子页面的控制台入口链接 | 单独 GET 后取得该主机的多厂商聚合与分发说明，判为确认，0.90。 |
| `api1.uiuiapi.com` | 种子页面的备用入口链接 | 单独 GET 后取得该主机的多厂商接入说明，判为确认，0.90。 |

新候选另建批次，使用其自身材料和带链接的关联材料进行分析，没有复制种子标签。完整关联记录见 [expansions.json](expansions.json)。本轮到此结束，没有递归扩大采集范围。

## 四、误报与漏报分析

以下区分“容易误报的相似站点”和“可能被遗漏的候选”。可能漏报不表示已经证明该域名真实属于中转站，更不代表已有可计算的漏报率。

| 类型与案例 | 本次结论及误判原因 | 处理与改进 |
| --- | --- | --- |
| 易误报：`docs.newapi.ai` | 排除，0.90。[文档](https://docs.newapi.ai/zh/docs)包含网关、上游渠道、令牌等词语，容易把软件能力误认为文档站经营的服务。 | 依据开源软件和自行部署说明修订模型解释。后续继续区分“软件能做什么”与“当前主机实际提供什么”。 |
| 易误报：`www.cherryai.com` | 排除，0.90。[下载页](https://www.cherryai.com/download)说明产品是桌面客户端；支持多个模型并不等于网站提供中转 API。 | 按客户端用途排除。判断时检查服务交付形式，不能只统计模型名称。 |
| 可能漏报：`gptgod.cloud` | 疑似，0.75。目录有中转收录，但当前静态页面只显示 Shell API 宣传和 JavaScript 提示。若仅导出确认类，潜在目标会被遗漏。 | 本次保留疑似及来源。后续可低频查看公开渲染页面或调用文档，补证后建立新批次；不能直接把通用模板升级为确认。 |
| 可能漏报：`api.nio.gs` | 疑似，0.55。[当前公告](https://api.nio.gs/)说明管理面板迁移，并声称旧 API 仍可用。只看旧首页，可能漏掉迁移后的服务。 | 保留迁移线索及旧域疑点。后续应核对公告中的新入口并独立取证；本次没有将新主机的业务反向赋给旧主机，也没有将其纳入已完成扩展。 |

此外，第三方目录的覆盖偏向公开列出的服务；私域推广、登录后才显示业务和没有种子链接的站点可能未进入候选集。当前 55 个域名属于定向样本，不能外推为全网规模或总体准确性。

## 五、持续生产与复现方式

当前原型采用人工定期启动的批次流程，没有定时调度服务。后续生产沿用同一条链路：更新公开候选，低频采集，检查摘录和来源属性，运行分析，复核疑点，整理一轮关联线索，再导出。需要补证、复验或变更规则时建立新批次，保留此前记录；单纯重跑模型不能代替获取新证据。

交付中的 [intelligence.json](intelligence.json)包含全部 55 条七字段情报；[summary.json](summary.json)记录统计和各域名采用的批次；`batches/` 保留原始分析，`reviews.jsonl` 保留实际复核记录。核对一条结论时，可从事实引用的 `material_id` 找到原文、来源网址和采集时间，再对照复核理由。

安装依赖并填写 `config/ai.json` 后，可以使用随附的固定输入重新分析。以下命令在项目根目录执行，批次名需要尚未使用：

```powershell
uv run --no-sync relay-intel run --run-id verify-001 --leads delivery/inputs/leads.jsonl --materials delivery/inputs/materials.jsonl
uv run --no-sync relay-intel resume --run-id verify-001
uv run --no-sync relay-intel export --run-id verify-001
```

`resume` 用于中断后的继续执行；新分析可能产生新的待复核项，应按 README 的复核流程处理后再作为完整交付。模型输出不保证逐次相同，但固定输入、引用检查、判定规则和原始记录能够支撑对差异的追查。未来引入人工抽检时，应先建立独立标签，再评估误报、漏报并调整标准。
